# 速译功能迭代建议 v3

> 日期：2026-09-22  
> 依据：当前代码、README、需求文档，以及 `功能升级建议-竞品调研-v1.md`、`改进建议-v2-功能与使用方式.md`  
> 性质：建议清单，不是已承诺需求。v1/v2 已落地的触发方式、档案、词典、Anki、历史分组、OCR 等不再重复。

## 0. 核心判断

速译的功能广度已经进入第一梯队：热键、悬停、双击、侧键、剪贴板、OCR 钉图、多引擎、TM、术语、词典、Anki、档案、本地 API 都已经具备。

下一阶段不应继续优先增加入口，而应集中解决三个更高价值的问题：

1. **把软件做成可长期安全更新的产品**：更新、回滚、备份、迁移、自诊断。
2. **把一次性译文变成可纠正、可复用的资产**：原位替换、译文纠错、TM 质量反馈、术语升级。
3. **把长内容与外部集成做成正式工作流**：字幕/文档翻译、批量任务队列、API v2/插件。

如果只做三项，我建议按以下顺序：

1. 签名自动更新 + 数据备份/恢复。
2. “翻译并替换选中文本”的原地工作流。
3. 可编辑 TM + 术语表 v2，让用户能纠正并持续提高后续结果。

## 1. P0：发布可靠性与系统韧性

### 1.1 签名自动更新、便携模式、失败回滚

需求文档中的 FR-023 仍未落地。现在每次修复都只能手工分发，这会成为后续迭代的最大瓶颈。

建议一次做完整闭环：

- 更新清单：版本号、最低兼容版本、SHA-256、下载地址、发布说明。
- 安装包和更新清单使用 Authenticode 签名，启动更新前校验签名与哈希。
- 下载到临时目录，退出主进程后原子替换；替换失败自动恢复上一版本。
- 保留上一个可用版本，支持“回滚到上一版”。
- 便携模式：配置、历史、模型缓存可切换为 EXE 同目录。
- 更新前自动创建一次轻量备份，升级失败不得丢设置与历史。

这是生产化优先级最高的一项，收益高于任何单个翻译功能。

### 1.2 一键备份 / 恢复 / 数据库维护

当前数据以本地文件为主，这是产品优势，但缺少完整迁移与恢复入口。

建议增加“设置 → 数据与备份”：

- 导出/导入：设置、场景档案、术语表、生词本、历史记录。
- 备份格式建议为带版本号的 ZIP，不包含明文 API Key；机器相关密钥仍由 DPAPI 保护。
- 数据库升级前自动备份，保留最近 3 份。
- 提供“检查数据库、压缩数据库、重建索引”入口。
- 导入时展示差异摘要，允许合并或覆盖，不静默清空现有数据。

不建议做账号云同步。手工备份既能满足迁移需求，也不会破坏“本地优先”的品牌承诺。

### 1.3 一键诊断 Doctor

很多支持问题来自环境而不是代码：

- 热键被占用；
- 目标应用与速译权限级别不一致，UIPI 导致取词失败；
- OCR 语言包缺失；
- PaddleOCR/ONNX 原生库加载失败；
- 代理、API Key、端点不可达；
- 本地 API 端口被占用；
- 配置、数据库路径不可写。

建议做“诊断中心”，逐项显示状态和可执行修复建议，并允许导出**脱敏诊断包**。诊断包包含版本、系统、日志摘要、配置状态，不包含原文、译文、API Key、Token。

### 1.4 OCR 原生引擎进程隔离

当前 PaddleOCR 已正确处理超时后的会话销毁，但原生推理仍在主进程内执行。如果原生库卡死或崩溃，进程仍可能长时间占用锁或直接终止应用。

更稳妥的升级是把 Paddle/ONNX 放进独立 Worker 进程：

- Worker 崩溃不影响主程序。
- 超时可直接终止 Worker，并按现有路由降级到 Windows OCR。
- Worker 可按需启动、空闲退出，继续满足内存与启动成本要求。
- Windows OCR 仍保留在进程内，不需要为默认路径增加成本。

这是少数值得“工程投入较大但长期收益明确”的优化。

## 2. P1：翻译结果的纠正与复用闭环

### 2.1 翻译并替换选中文本

这是当前最值得补的核心工作流。现有流程是“选中 → 翻译 → 看小窗 → 复制 → 回到原应用粘贴”，步骤仍然偏多。

建议增加可选的“翻译并替换”动作：

- 复用现有划词取词链路；
- 翻译成功后直接把结果写回原编辑位置；
- 写入前保留剪贴板与输入法状态；
- 支持撤销，且不破坏用户原有剪贴板；
- 首版只处理纯文本，富文本/表格保留给后续版本；
- 默认关闭，避免用户误替换。

可放在托盘、快捷动作菜单或用户自定义热键中。成功后用户从三次以上操作降到一次触发。

### 2.2 可编辑 TM 与译文纠错

当前 TM 只会自动复用历史，缺少“这条历史是错的，别再用了”的反馈通道。

建议把历史扩展为可管理的翻译记忆：

- 历史译文可直接编辑并保存。
- 增加“已校对 / 待校对 / 禁止复用”状态。
- 用户修完译文后，可选择“保存为高质量 TM”。
- TM 命中时显示来源、校对状态和时间。
- 精确命中优先于模糊命中；高质量记录优先于同文本的旧记录。
- 纠错后可提示“是否加入术语表”。

需要给 `IHistoryRepository` 增加更新能力；当前接口只有搜索、删除和清空。这个功能会让 TM 随着使用越来越可靠，而不是越来越脏。

### 2.3 术语表 v2

当前术语表是简单源词到译词的全局映射，适合轻量场景，但专业用户很快会碰到边界。

建议升级：

- CSV/TSV 批量导入导出，兼容 Excel。
- 术语包按行业或项目组织，可启用/停用整包。
- 作用域：全局、语言对、场景档案、指定引擎。
- 匹配方式：普通词、仅整词、区分大小写、正则。
- 类型：必须使用、优先使用、禁止使用。
- 冲突预览：导入前展示重复、反向冲突和包含关系。
- 命中详情进入结果审计信息，而不只是一枚“术语 ×N”。

这会直接把“术语表功能”升级成可维护的专业词库。

### 2.4 LLM 流式输出与成本预算

当前 LLM 请求固定 `stream=false`，长文本会一直等到完整结果才显示。

建议增加：

- 可选流式响应，译文区渐进显示；取消、换会话、关窗仍走现有会话版本控制。
- 解析兼容接口返回的 token usage。
- 本地记录请求数、输入/输出 token、预计费用；用户自行配置每百万 token 价格。
- 每日/每月预算提示，超限前警告，不自动扣费或修改用户端点。
- 对完全相同的输入提供可选精确缓存；隐私模式和历史关闭时不落缓存。

这项优化同时改善感知速度、成本可控性和专业用户信任。

## 3. P2：长内容与生态能力

### 3.1 字幕与文档工作流

PDF/EPUB 完整保留排版工程量大，不建议直接作为第一步。更合理的是先做“分段翻译 + 对齐导出”：

- 第一批：SRT、VTT、TXT、Markdown。
- 第二批：DOCX，保留段落标记；导出原文/译文/双语三种模式。
- 字幕保留时间轴和序号，只替换文本。
- 文档使用稳定的 segment id，支持逐段重试、锁定已人工校对段落。
- PDF/EPUB 后续再进入排版级翻译。

这比直接承诺“PDF 完美保留排版”更可控，也能先验证长内容需求。

### 3.2 批量任务队列

现有批量 OCR 已能逐图识别并导出 Markdown，可进一步抽象成统一任务系统：

- 支持多图片、TXT、Markdown、SRT；
- 文件夹拖入和目录监听；
- 暂停、取消、失败重试；
- 只重试失败项；
- 每个任务独立进度和错误摘要；
- 输出任务报告，便于批量处理 Ozon listing 或文档素材。

这可以复用现有 OCR、翻译、导出管线，不需要重新发明核心引擎。

### 3.3 本地 API v2

当前 API 只有 `/api/status` 和 `/api/translate`，适合最小集成，但还不足以承接插件生态。

建议扩展：

- OCR 与词典接口。
- `Authorization: Bearer` 替代或兼容现有 `X-Auth`。
- OpenAPI JSON，方便脚本、AutoHotkey、浏览器扩展接入。
- 请求 ID、并发限制、速率限制和错误码规范。
- SSE 流式翻译接口。
- 支持显式指定 profile、引擎、目标语言和是否允许术语/TM。
- 隐私模式状态可查询，隐私模式下按既有规则直接拒绝或关闭监听。

之后再做“插件式引擎脚本”，风险会比现在直接做低很多。

## 4. P3：战略押注，先做探针

- PDF/EPUB 保留排版双语对照。
- 端侧小模型离线翻译，前提是单文件体积与内存预算可控。
- 插件式引擎脚本，承接 Pot 归档后的开发者需求。
- 完整的单词熟悉度/遗忘曲线复习系统。
- 多设备手工同步包，仍坚持不建立云端账号体系。

这些项目不应先写大需求，先做一到两周技术探针验证体积、性能、交互和真实使用频率。

## 5. 明确不建议

- 账号、云同步、云端保存用户文本：与本地优先定位冲突。
- 实时会议同传：与“几秒即走”的桌面工具定位偏离。
- 广告、会员弹窗、强制登录：直接破坏当前信任优势。
- 为了功能数量继续增加热键入口：入口已经足够，下一步应降低单次工作流步骤。

## 6. 推荐实施顺序

### 第一批：生产化底座

签名更新与回滚 → 便携模式 → 数据备份/恢复 → Doctor 诊断 → OCR Worker 隔离。

### 第二批：质量闭环

翻译并替换 → 可编辑 TM → 术语表 v2 → LLM 流式与费用预算。

### 第三批：长内容与生态

SRT/VTT/TXT/Markdown → 批量任务队列 → 本地 API v2 → DOCX → 插件式引擎。

### 第四批：战略探针

PDF/EPUB、端侧离线翻译、完整复习系统。

## 7. 建议观测指标

- 更新成功率、回滚成功率、升级后数据完整率。
- 取词失败后的诊断定位率。
- 翻译替换的平均操作步数与撤销成功率。
- TM 纠错后再复用比例、禁用译文比例。
- 术语冲突数量与导入成功率。
- LLM 请求 P50/P95 延迟、token 与费用趋势。
- OCR Worker 超时隔离成功率与回退成功率。
- 长文档/字幕任务失败重试成功率。
